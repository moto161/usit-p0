## 2. Current implementation facts

Reviewed files at HEAD `80a3cc0`:

- `usit/test_report_adapters.py`: pytest JSON adapter retains `nodeid`, outcome-derived status, and counts. It does not currently preserve a report-provided source path, line, qualified symbol, or execution snapshot identifier.
- `usit/test_result_importer.py`: explicit mapping may declare `test_source_file`, `test_source_line`, and `test_source_file_sha256`. Import verifies the referenced file bytes and that the line is within the file. It does not parse the language or prove the line declares the mapped test symbol.
- The mapping is external to the test execution report. A matching mapping digest is therefore not independent proof that the test process executed that byte snapshot.
- JUnit testcase identity is derived from classname/name; pytest identity is the nodeid. Neither identity alone proves a source symbol was loaded or executed.

### What existing status proves

`TEST_SOURCE_BYTES_MATCHED` means only that the importer read a file under the explicit project root whose bytes matched the digest declared in the mapping, and that the declared line is in bounds.

It does NOT prove:
1. that the line is the start of the named test function/method;
2. that the report testcase ID was produced by that exact symbol;
3. that the test process loaded the same source bytes;
4. that the report and current project root represent the same source snapshot;
5. that the test meaningfully exercises the intended business behavior.

Do not rename, reinterpret, or promote this status to a symbol-verified or execution-snapshot-verified status.

## 3. Required evidence dimensions

Keep these dimensions independent in every result and verifier:

| Dimension | Suggested states | Evidence source |
|---|---|---|
| Execution outcome | PASSED / FAILED / SKIPPED / ERROR / UNKNOWN | Test report |
| Report-to-run provenance | MATCHED / MISSING / MISMATCH / INVALID | Runner-generated execution record plus report digest |
| Source snapshot provenance | MATCHED / MISSING / MISMATCH / INVALID | Runner-generated immutable source manifest captured for the run |
| Source bytes | MATCHED / HASH_MISMATCH / MISSING / NOT_CHECKED / INVALID | Safe importer read of exact path and bytes |
| Source symbol | VERIFIED / MISMATCH / NOT_SUPPORTED / NOT_PROVIDED / NOT_VERIFIED | Parser-backed symbol resolution plus report/runner locator |
| Business mapping | VERIFIED / CONFLICT / UNVERIFIED | Reviewed mapping plus independently verified graph/evidence |

A success in one dimension must never imply success in another. Missing evidence must remain explicit and fail closed for any derived measured/verified conclusion.

## 4. Execution provenance record contract

Introduce a versioned record generated by the controlled test-runner wrapper, not authored solely by a mapping file. Initial proposed schema identifier: `usit-test-execution-provenance-v1`.

Minimum required fields:

- `schema_version`: exact version identifier.
- `execution_id`: unique opaque run identifier.
- `started_at` and `completed_at`: UTC timestamps; completed must not precede started.
- `runner`: normalized runner name and version.
- `report_format`, `report_relative_path`, `report_sha256`.
- `source_snapshot`: manifest schema/version, canonical manifest digest, file count, and explicit capture method.
- `working_tree_state`: clean/dirty/unknown plus explicit treatment of untracked files; never label dirty or unknown as a reproducible snapshot.
- `command_fingerprint`: normalized test command/arguments with secrets and environment values excluded.
- `environment_fingerprint`: allowlisted runtime/platform/toolchain versions only; no credentials or arbitrary environment dump.

Trust requirements:

1. The runner creates the record at execution time and hashes the completed report after the runner exits.
2. The source manifest is captured from the exact source tree made available to the test process; it must account for tracked, untracked, generated, and ignored files that can affect execution, or explicitly state which classes are outside the guarantee.
3. The report and provenance record are finalized together in a run output directory. The importer verifies the report hash before parsing.
4. Import must not silently substitute the current checkout for the captured source snapshot.
5. A user-supplied record with no authenticated/controlled runner provenance may be parsed as untrusted evidence, but cannot establish `MATCHED`.
6. Avoid claiming cryptographic authenticity merely because a JSON record contains hashes. Integrity, origin, and source snapshot capture are distinct guarantees.

## 5. Source-symbol verification contract

For supported languages, resolve the report/runner-provided locator against the exact source bytes already verified by the importer:

- Python: AST-based qualified function/method lookup, including class nesting and decorators; line must fall within the resolved definition span.
- Other languages: add parsers incrementally only where the repository has a reliable parser dependency and tests. Do not use regex as a substitute for syntax-aware symbol identity.
- Unsupported languages, generated/dynamic test cases, parameterized cases whose runtime identity cannot be mapped unambiguously, and report formats without source locators remain `NOT_VERIFIED` or `NOT_SUPPORTED`.
- Never infer a source symbol solely by stripping a pytest nodeid or splitting a JUnit classname/name.
- Preserve raw report identity separately from normalized symbol identity.

The first implementation slice should support Python/pytest only if the runner can provide trustworthy source locator data. JUnit remains execution-outcome-only unless a controlled runner extension can provide equivalent provenance.

## 6. Required adversarial regression tests

At minimum:

1. Valid source digest + in-bounds line that points to the wrong function: symbol verification must fail.
2. Correct function exists elsewhere in the file but mapping line points to another symbol: fail.
3. Report nodeid/testcase ID disagrees with the runner's symbol locator: provenance conflict; no verified mapping.
4. Report bytes changed after provenance record creation: report digest mismatch; reject import.
5. Source file changed after test execution but before import: execution snapshot remains tied to captured manifest; current checkout mismatch must not be silently accepted.
6. Same report imported against another source manifest: snapshot mismatch.
7. Missing, malformed, duplicate, or unsupported provenance record: no verified execution/source claim.
8. Parameterized pytest nodeids: preserve raw nodeid; resolve the underlying function only when runner evidence identifies it unambiguously.
9. Symlink/reparse, path traversal, ADS/drive-relative path, oversized manifest, duplicate paths, and case-collision paths remain rejected or explicitly ambiguous across supported platforms.
10. A passing execution with invalid source provenance remains PASSED for the report outcome but UNVERIFIED for source identity and business evidence.

## 7. Implementation sequence and stop conditions

1. Define schema and canonical serialization/digest rules; add parser/validator unit tests.
2. Add a controlled Python/pytest runner wrapper that captures source manifest before execution, runs tests against that snapshot, hashes the report, and writes the provenance record. Do not claim reproducibility if tests can mutate source during execution; detect and fail/mark dirty.
3. Add importer support for an explicit provenance record path and verify report digest, source manifest digest, run identity, and path safety.
4. Add AST-based Python test symbol verification from runner-provided locators.
5. Extend the business evidence verifier to preserve separate statuses and fail closed on any missing/conflicting dimension.
6. Add adversarial tests before enabling any measured/verified status.
7. Run focused tests, full supported suite, Linux and Windows required workflows, and inspect non-gating baseline diagnostics separately.

STOP conditions:
- No source snapshot guarantee when runner cannot control or identify the actual files loaded by the test process.
- No symbol VERIFIED status when source locator is mapping-authored only or parser resolution is ambiguous.
- No report/run MATCHED status without report digest verification against the runner-generated record.
- No broad exclusions, frozen-hash rewrites, or CI weakening to obtain green status.

## 11. Controlled pytest runner — first implementation (2026-11-03)

Implemented on feature/understanding-to-test-v1 after the initial contract review.

### Code and behavior

- usit/controlled_pytest.py adds run_controlled_pytest.
- usit run-pytest is an explicit CLI entry point. It requires an external usit-test-execution-authorization-v1 record bound to the exact project root and evidence parent, an explicit allowed action, an acknowledgement that project code will execute, an approval reference, and a live UTC authorization window.
- The runner requires a clean Git worktree, rejects tracked changes and untracked files, rejects Git submodules, and rejects symlinks/special files in the Git archive. It runs git archive HEAD into a fresh staging directory and launches python -m pytest against that staged copy using argv (no shell), a bounded timeout, a reduced environment, and a constrained pytest option allow-list.
- The run uses the existing verification_capture.capture_run engine for pre/post hashes, stdout/stderr, timeout/interruption handling, source-change detection, and evidence-manifest verification.
- The evidence bundle preserves the exact archived source under source_snapshot/, and includes source-manifest.json, junit.xml, execution-provenance.json, capture snapshots/logs, final_gate_report.json, and a unified SHA-256 evidence manifest. Source files are individually listed in the evidence manifest.
- The original project directory is not the test working directory. The staged source copy is separate; any tracked source mutation during execution fails the gate. Untracked worktree content is refused before archive creation rather than silently omitted.
- Pytest is pinned to 8.3.5 in pyproject.toml and the Linux/Windows CI setup. New regression coverage includes successful staged execution, retained snapshot bytes, dirty/untracked refusal, explicit authorization acknowledgement, reserved-option rejection, failed test outcome, and source mutation during execution.

### Trust boundary and remaining gaps

- This runner is not an OS sandbox. It does not technically block network access, host-resource access, or every possible credential access by arbitrary test code. The reduced environment removes inherited API-key-style variables but must not be represented as a security sandbox. Authorization must be explicit and informed.
- Runner authenticity remains UNAUTHENTICATED. Hashes prove consistency of the evidence bundle, not the identity or integrity of the runner executable.
- The runner executes committed Git HEAD only. Dirty/untracked worktrees and submodules are refused; ignored local files are not part of the Git archive. Project dependencies must already be installed; no dependency installation is performed.
- STAGED_SNAPSHOT_USED_UNAUTHENTICATED means the runner's declared execution path used a staged Git archive. It is not an authenticated source-loaded proof.
- JUnit outcome is now generated by the controlled runner, but pytest source-symbol properties are not yet bound into the report. The importer can compare a reviewed mapping's source file digest to the preserved snapshot and can AST-check a declared line/symbol against that snapshot, but the report-to-symbol identity relationship still needs runner-origin evidence.
- Business-function correctness still requires a reviewed mapping, expected-result oracle, and independent test/coverage/runtime evidence checks.

## 12. Pytest source locator and complete evidence-bundle import (2026-11-03)

The controlled runner injects a pytest plugin into the staged execution tree. For each executed test call, it adds these JUnit testcase properties:

- usit_source_file
- usit_source_line
- usit_source_symbol
- usit_nodeid

The plugin source is retained as runner-plugin.py, and its SHA-256 is recorded in provenance runner metadata and checked against the evidence manifest during import. The importer parses these fields without treating them as authenticated facts. It compares them with the reviewed mapping and emits REPORT_SOURCE_LOCATOR_MATCHED_UNAUTHENTICATED or REPORT_SOURCE_LOCATOR_MISMATCH. The mapping must explicitly carry the source path, line, qualified symbol and exact pytest nodeid for this comparison.

The importer now accepts an optional evidence_dir. When supplied together with the provenance record and source manifest, it:
- requires the report, provenance record and source manifest to be the exact files inside the selected evidence bundle;
- verifies the entire evidence_manifest.json and every artifact hash;
- requires project_root to be the bundle's source_snapshot directory;
- verifies that the source manifest and the complete source_snapshot artifact set match exactly;
- checks each source-manifest file digest against the preserved source_snapshot artifact;
- verifies runner-plugin.py against runner.plugin_sha256 when declared.

This establishes integrity consistency across the bundle and enables AST checks against the preserved source snapshot. It does not authenticate the runner or prove that a hostile test process could not manipulate runtime state. Report locator equality is explicitly UNAUTHENTICATED and cannot promote a business function to VERIFIED.

End-to-end regression coverage now exercises: staged pytest execution → JUnit source locator properties → preserved snapshot → full evidence-bundle verification → explicit mapping → Python AST declaration check → business-function execution result. The execution outcome and the separate source/mapping/authenticity statuses remain independent.
